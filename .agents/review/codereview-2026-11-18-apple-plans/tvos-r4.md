## Additional findings in the changed text

### Playlist sync

1. **HIGH — A correctly linked TV can lack the identity needed to open a shared entry.** The plan reuses the existing sign-in flows. Plex links save the machine ID but discard the account ID. Jellyfin and Emby links save the user ID but discard the server ID. After relaunch, a TV using those records alone cannot match the required tuple, even for the correct user. Capture the authenticated provider IDs at linking, retain a local mapping, and backfill existing connections on an authenticated reconnect. Keep unmatched entries visible as unavailable. [tvos-port.md:357](/Users/michael/Dev/vela/.agents/plans/tvos-port.md:357) · [tvos-port.md:439](/Users/michael/Dev/vela/.agents/plans/tvos-port.md:439) · [commands.rs:1672](/Users/michael/Dev/vela/src-tauri/src/commands.rs:1672) · [jellyfin.rs:637](/Users/michael/Dev/vela/src-tauri/src/source/jellyfin.rs:637)

2. **MEDIUM — Two accepted moves can produce different playback order on different TVs.** Two offline TVs can place different entries in the same gap and independently generate the same position key. The writes affect different CloudKit records, so neither needs to produce a record conflict. Sorting by position alone leaves the next title ambiguous. Define a total order, such as position key followed by stable entry ID, and use it for display, playback and subsequent moves. [tvos-port.md:368](/Users/michael/Dev/vela/.agents/plans/tvos-port.md:368) · [tvos-port.md:483](/Users/michael/Dev/vela/.agents/plans/tvos-port.md:483)

3. **MEDIUM — Deleting a playlist has no rule for its separately stored entries.** If one TV deletes the playlist while another has an append pending, independent entry records can survive or arrive after deletion and consume private-database quota. Choosing CloudKit’s direct `deleteSelf` relationship for every entry introduces its own limit of 750 incoming references. Give entries an explicit playlist identity, make deletion win over late edits, and reclaim the entries in retryable batches. ### Shared engine used by tvOS

4. **HIGH — The specified tvOS bridge cannot serve the engine’s first media read.** The shared engine now requires Rust to fetch byte ranges. The tvOS ABI enumerates JSON commands, player events, lifecycle calls and a dedicated artwork reader. It defines no media-read operation. Implementing T2 as written leaves T6 unable to fetch even the first part of a direct play through the required transport. Add a session-scoped binary media reader to the ABI, with bounded reads, cancellation and an explicit owner for returned buffers. [ipados-port.md:289](/Users/michael/Dev/vela/.agents/plans/ipados-port.md:289) · [tvos-port.md:243](/Users/michael/Dev/vela/.agents/plans/tvos-port.md:243) · [tvos-port.md:249](/Users/michael/Dev/vela/.agents/plans/tvos-port.md:249)

5. **HIGH — Reusing the provider HTTP client does not honor the player’s certificate setting.** The changed plan says the client already honors it. The Plex and Jellyfin clients are built with default trust and a 15-second request timeout. The certificate preference is read separately at player launch. A media endpoint requiring the approved override can therefore fail at Play, and a slow but progressing media response can hit the metadata client’s deadline. Build a playback-specific client from the `PlayRequest` policy, keep verification enabled by default, handle redirects explicitly, and use timeouts appropriate for streaming. 8. **HIGH — A resume point can become stale while the restored player is paused.** The plan chooses the position on foreground return.
