### Local playback and renderer selection

1. **HIGH — The shipping build excludes codecs the owner requires.** A-2 gives examples of software-decoded formats, but A-3 enables *only* the components A-2 names. An FFV1 video in an MKV is a concrete failure. FFmpeg has a decoder, yet the prescribed build omits it, leaving an Original-quality play with no decoder. Enable the local decoder and input-format coverage required by the ruling, within the existing licensing rules. Treat A-2’s examples as routing examples rather than a build allowlist. 2. **HIGH — The Dolby Vision decision can select the wrong renderer for ordinary video.** The decision limits loopback to Dolby Vision, yet A-2 sends compressed video, including VP9, through whichever renderer P2 chose. Apple’s HLS video formats exclude VP9. P2 also directs software-decoded video through both renderers even though the plan says loopback cannot display those frames. Use sample buffers for ordinary video and all software-decoded frames. Make P2’s result specific to the Dolby Vision profile and device, and carry that distinction into iPhone C1’s memory budgets. ### Network input

8. **HIGH — App Transport Security can block the new media client.** The plan moves media requests to `URLSession`, while its transport exceptions cover web-view loads and local networking. A user-configured HTTP server on a fully qualified hostname can therefore browse through the Rust client and fail when playback starts. An ATS-protected HTTPS host can also defeat the promised certificate setting. Use a media transport that can honor the configured server policy, such as the Rust transport already contemplated by B-1, and retain the per-request origin and redirect checks. [ipados-port.md:305](/Users/michael/Dev/vela/.agents/plans/ipados-port.md:305) · [ipados-port.md:315](/Users/michael/Dev/vela/.agents/plans/ipados-port.md:315) · [ipados-port.md:553](/Users/michael/Dev/vela/.agents/plans/ipados-port.md:553) · [Apple’s web-content exception](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppTransportSecurity/NSAllowsArbitraryLoadsInWebContent) · [Apple’s server-trust rules](https://developer.apple.com/documentation/foundation/performing-manual-server-trust-authentication)

9. **HIGH — FFmpeg’s default HLS connection reuse can terminate the app with custom I/O.** The plan keeps FFmpeg’s HLS demuxer and HTTP protocol enabled while supplying a custom byte reader. FFmpeg 9 enables HLS HTTP persistence by default. When it reuses a playlist or segment reader, it asserts that the reader has a native FFmpeg URL context. Vela’s reader lacks that context, so ordinary HLS playback can abort the process. Disable the demuxer’s native HTTP persistence for this adapter and let the engine’s HTTP client pool its own connections. 10. **MEDIUM — The byte reader loses the base URL of a redirected playlist.** If a server redirects a playlist to another directory and that playlist contains relative segment names, the bytes alone do not tell FFmpeg where to resolve them. Its native reader normally exposes the final URL through `location`. With the proposed handoff, the next request can go to the old directory and return 404. Resolve every playlist reference against the final response URL before cleaning it, or convey that effective URL to the demuxer. 11. **MEDIUM — Fetching a segment by URL loses HLS byte-range semantics.** Several segments can occupy different byte ranges of the same fragmented MP4 resource. FFmpeg passes start and end offsets to the I/O adapter and assumes an HTTP reader has applied them. Fetching each URL from byte zero can repeat the first fragment or fail decoding. Carry the requested byte interval through the adapter and verify which interval the server returned before handing bytes to FFmpeg. ### Playback recovery

12. **HIGH — A foreground termination can lose the transcode cleanup record.** Lifecycle transitions are the only explicit checkpoint write trigger. If iOS terminates Vela during playback before the next transition, the current position and a newly started server encoder can exist only in memory. The next launch then lacks the identifier needed to stop that encoder. Persist the session and cleanup identifier as part of starting a transcode, write coalesced position updates during active playback, and flush again at lifecycle transitions. Keep that checkpoint separate from settings history. 13. **HIGH — A freshness check cannot protect a later unconditional Plex write.** The plan permits replaying old progress if the server has nothing newer. Another device can update the item after that check and before Vela’s write. The existing Plex request sends the item key and position with no revision precondition, so the delayed request can still overwrite the owner’s newer progress. Use a provider-side conditional update where available. Where freshness cannot be enforced at write time, retire the ambiguous old progress write and finish session-specific cleanup independently.
