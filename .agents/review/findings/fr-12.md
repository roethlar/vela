## Evidence

## Predicted observable failure

Reviewer, verbatim: "An architecture-specific compilation error on the non-host Darwin target passes this CI job and first fails during the tagged universal release build, defeating the new pre-release compilation gate."

Reviewer's suggested direction, verbatim: "Install both Darwin targets in CI and run cargo check --locked explicitly for each."

## What

Admitted: the `other-platforms` job the working agent added at `687d533`
runs `cargo check` for the runner's own architecture only, while the release
builds a universal app from both `aarch64-apple-darwin` and `x86_64-apple-
darwin`. A compile error on the other one would first show in the tagged
release build, which is what the job was added to prevent.

## Approach

What landed (`ceed9be`), in its commit's words:

The job added at 687d533 to compile the backend off Linux between
releases ran `cargo check` for the macOS runner's own architecture only.
The release builds a universal app from aarch64-apple-darwin and
x86_64-apple-darwin, so a compile error on the other one would first
have shown in the tagged release build, which is what the job is there
to prevent (review finding fr-12).

The job now installs both targets on macOS and checks each by name;
Windows keeps its host check. tests/release-workflow.test.mjs holds it:
both targets installed, each checked explicitly, the host-only check
scoped to Windows.

Written by codex; reviewed by the working agent: with ci.yml put back to
what it was, the four new tests fail and the three older ones pass; with
the repair, seven of seven. Whether both checks run and pass on GitHub's
runner is seen in this commit's own CI run.
