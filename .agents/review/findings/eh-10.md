# eh-10: Continue Watching restarts local items from 0:00

**Severity**: HIGH — "Continue Watching" is the product's core resume surface, and for the entire local family (local folders, SMB, SSH) clicking it restarted the video from the beginning
**Status**: Verified
**Branch**: n/a — no-branches adaptation; fix lands as a single commit on `main`
**Commit**: `4527613`

## Evidence
`src-tauri/src/source/local.rs:855,863` — the local provider hardcodes
`resume_ms: 0`; `src-tauri/src/commands.rs` (`play_by_key`, pre-fix) used
only `resolved.resume_ms` for `--start`. Vela's own recents stamp
(`viewOffsetMs`, written at every mpv exit and displayed as the hero's
progress ring) was never consulted. Trigger: play a local file, quit
mid-way, click the item in the Continue Watching hero. Found by the
slice-4 E2E resume scenario: red run transcribed
`resume must start at the stamped 7500ms, got 0.25s`.

## Predicted observable failure
A local-only (or SMB/SSH) user quits a film halfway, later clicks it in
Continue Watching — and it restarts at 0:00 while the card shows the
correct progress percentage. Contradicts the 2026-07-04 hero decision,
whose stated purpose is source-agnostic continue-watching independent of
server thresholds.

## What
The resume path trusted only server-provided positions; sources with no
server-side progress store had no resume at all despite Vela stamping one.

## Approach
New `recents::resume_stamp_ms(cfg, key)` returns Vela's stamped position
for a key (matching either identity of a merged item, via the existing
`entry_matches`); `play_by_key` falls back to it when the provider
resolves `resume_ms == 0`. A server-supplied position still wins — the
server stays the watch-state authority; the stamp only fills the gap it
was invented for. Finished entries are dropped at stamp time, so there is
no resume-at-EOF trap.

## Files changed
- `src-tauri/src/recents.rs` — `resume_stamp_ms` + unit test
- `src-tauri/src/commands.rs` — fallback in `play_by_key`

## Guard proof
Two layers, both executed 2026-07-05:
- Unit: `resume_stamp_reads_back_the_finished_position` — sabotaging the
  helper to return 0 fails the test; restored, 81/81 pass.
- E2E (`tests/e2e/scenarios/resume.mjs`, landing with the slice): red
  against the pre-fix app (`stamped 7500ms, got 0.25s`); green after —
  the hero replay's first mpv `time-pos` sample lands within 1.5s of the
  stamp, and a fresh item still starts near 0.

None — coder-filed.

## Known gaps
When a server resolves 0 for a genuinely-unwatched item but a stale local
stamp exists, the stamp wins; the displayed hero state matches the stamp,
so behavior and UI agree. Merged-item override paths route through the
same key matching as other curation ops (cw-1 precedent).
