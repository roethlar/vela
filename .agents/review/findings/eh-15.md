# eh-15: Badge assertions can pass before the post-refetch card state is proven

**Severity**: MEDIUM — a regression where the refetch restores the old watch state (or drops the card) stays green: the wait is satisfied by the optimistic local mutation or by the empty grid during the refresh gap
**Status**: Open
**Branch**: n/a — no-branches adaptation; fix lands as a single commit on `main`
**Commit**: (filled in after commit)

## Evidence
`tests/e2e/scenarios/markwatched.mjs` (pre-fix) — the unwatch wait is
`!card?.classList.contains('watched')`, truthy when the card is MISSING
and immediately after `setWatched`'s optimistic `item.played = played`
(`src/routes/+page.svelte:737`) — before `refreshWatchState()` →
`resetAndLoad()` clears and reloads the grid. `driver.waitFor` returns on
the first truthy poll. The watched-direction wait has the mirrored hole
(optimistic badge before the refetch could clear it). Filed by codex in
the e2e-10 batch pass (unwatch leg); the coder extended it to the
mirrored watched leg.

## Predicted observable failure
A refetch that restores the previous watch state, or a refreshed listing
that drops the card, still exits 0 — the scenario claims "survives the
refetch" without ever observing post-refetch state.

## What
The waits don't distinguish optimistic UI state from refetched server
state.

## Approach
Track the mock's `/Users/{u}/Items` GET count: record it before each
mark action, wait for the action's PlayedItems request, then wait for a
LATER Items refetch, and only then assert the card is PRESENT and carries
(or lacks) the badge.

## Files changed
- `tests/e2e/scenarios/markwatched.mjs` — refetch-count gating + present-
  card badge assertions, both directions

## Guard proof
Deterministic red/green: with the mock temporarily inverting the
Played value it reports after a refetch (serving stale state), the
post-refetch assertion must FAIL in each direction; with the true state,
both PASS. Executed results transcribed below.
