# fr-10: a Jellyfin start report whose answer was lost is sent again, and the server counts the play twice

**Severity**: MEDIUM — A Jellyfin start report whose answer was lost is sent again, and the server counts the play twice.
**Status**: In progress
**Branch**: —

## Evidence

Reviewer, verbatim: "src-tauri/src/playback.rs:1645 applies the retry to the start POST at line 1656. If the server accepts that POST but its response is truncated, IncompleteMessage triggers another POST; a local TCP probe confirmed this replay. Jellyfin's OnPlaybackStart increments PlayCount on every call without deduplicating PlaySessionId. See [Jellyfin's implementation](https://github.com/jellyfin/jellyfin/blob/v10.10.7/Emby.Server.Implementations/Session/SessionManager.cs#L645-L719)."

## Predicted observable failure

Reviewer, verbatim: "One playback increments the persisted play count twice and emits duplicate playback-start events when the first response is lost."

Reviewer's suggested direction, verbatim: "Exclude start reports from retries after ambiguous delivery failures. Their first request already uses a fresh client; restrict retries to demonstrably idempotent operations or failures that prove nothing was sent."

## What

Admitted. The retry of e50aa83 was applied to every report, on the working
agent's own statement in that task that all of them are safe to send twice.

raises the item's play count on every call (the reviewer cites the server's
source). The start report is also the one report that cannot meet the fault
the retry was made for: it is the first request on a client just built, so
there is no pooled connection for the server to have closed.
