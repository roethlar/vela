# tr-10: a transcoded Plex play hands mpv the token in the URL

**Severity**: HIGH — the exact exposure the 2026-07-23 credential split was
built to remove, reintroduced on the transcode path only.
**Status**: Open — live safety gate satisfied 2026-07-26; fix not started
**Branch**: (not started)
**Commit**: (none)

## Evidence

`src-tauri/src/source/plex.rs:1423` initialises `stream_headers` empty.
`src-tauri/src/source/plex.rs:1469` populates it — `vec![("X-Plex-Token", …)]` —
but ONLY inside the `if url.is_empty()` branch, which is the direct-play path.

The transcode branch above it sets `url` from `PlexLibrary::transcode_url` and
never touches `stream_headers`. `transcode_url`
(`src-tauri/src/plex_library.rs`) puts `("X-Plex-Token", self.auth_token)` in the
query string, as its own unit test shows:

```
…&session=fef10294cad84a90a29f171d02bae78d&X-Plex-Client-Identifier=art-client&X-Plex-Token=synthetic-artwork-token
```

So `StreamResolution.http_headers` is EMPTY for a transcoded play, and the token
travels to mpv inside the URL instead.

Condition that triggers it: any Plex play where the resolved quality is a tier
rather than Original — the Settings quality setting, or a one-off from the
title's quality menu.

## Predicted observable failure

For a transcoded Plex play, the auth token is observable wherever mpv's
invocation or state is:

- mpv's `path` property, readable over its IPC socket;
- mpv's own log output if the user has logging enabled;
- the process argument list — `ps`/`/proc/<pid>/cmdline` shows mpv's argv, which
  on a multi-user machine is readable by other users.

A direct play is not observable this way: its URL is token-free and the token
rides a private per-launch header include. The live scenario planned for this
work can assert it directly — read mpv's `path` after starting a transcoded
play and check for `X-Plex-Token`. Today that assertion FAILS; after the fix it
must pass, which is the guard.

## What

The 2026-07-23 connection-split decision, recorded in
`.agents/repo-guidance.md`, states that the approved split "removes Plex tokens
from returned URLs and query parameters in favor of guarded request headers".
Slice 3 of server-transcoding honoured that for direct play and did not carry it
to the transcode path it added, so the transcode URL still authenticates the way
the whole credential effort moved away from.

## Approach

(not started — the code change still requires an approved plan)

The shape is: build the transcode URL WITHOUT the token parameter and return
`stream_headers` carrying `X-Plex-Token` exactly as the direct-play branch does,
so mpv authenticates through the same private header include for both delivery
modes.

The live safety gate is satisfied. Against the owner's Plex on 2026-07-26, a
one-off HLS session used the token only as `X-Plex-Token` request headers:

- the token-free master playlist returned 200;
- its token-free child playlist returned 200;
- a token-free segment request returned 206 and 1,024 bytes;
- neither generated child URI contained a token; and
- `DELETE /transcode/sessions/<id>` returned 204, with no probe session left.

Plex therefore accepts header auth throughout the HLS request chain. This can
be the same small header move used by direct play; it does not need a larger
authentication design.
