# eh-13: Mock stream mishandles Range edges — can crash the runner or send invalid 206s

**Severity**: MEDIUM — mpv/libavformat legitimately probes MP4 with suffix/EOF ranges; an edge hit crashes the mock (uncaught ERR_OUT_OF_RANGE in the server callback) or returns a lying Content-Length, failing `watchstate` for a harness bug
**Status**: Verified
**Branch**: n/a — no-branches adaptation; fix lands as a single commit on `main`
**Commit**: `526f511` + fix-up `d5e1b04` (reviewer reopen)

## Evidence
`tests/e2e/mockjf.mjs` (pre-fix) parses only `bytes=start-end`, never
clamps `end`, and pipes `fs.createReadStream(mediaFile, {start, end})`
unconditionally: `Range: bytes=<size>-` yields `start > end` and throws;
`bytes=0-999999999` advertises a span past EOF. The repo's own loopback
proxy implements the correct semantics (`src-tauri/src/stream_proxy.rs`
clamping + 416). Filed by codex in the e2e-8 batch pass.

## Predicted observable failure
A seek/probe pattern that emits a suffix or past-EOF range kills the Node
E2E process mid-run or feeds mpv a malformed partial response — a flaky
or fatal `watchstate` failure with no app regression behind it.

## What
The mock's Range handling covers only the happy shape the current mpv
build happened to send.

## Approach
Match `stream_proxy` semantics: parse `bytes=a-b`, `bytes=a-`, and
`bytes=-suffix`; clamp `end` to `size-1`; return `416` with
`Content-Range: bytes */size` when `start` is unsatisfiable; compute
Content-Length from the clamped span before piping.

## Files changed
- `tests/e2e/mockjf.mjs` — Range parsing/clamping/416

## Guard proof
Deterministic red/green via direct HTTP probes against the mock (node
one-liner, no mpv): pre-fix, `bytes=<size>-` crashes the server process
and `bytes=0-999999999` returns a Content-Length larger than the file;
post-fix, they return `416` and a clamped `206` respectively, and a
`bytes=-500` suffix returns the last 500 bytes. Scenario stays green.
Executed 2026-07-05: red — `bytes=<size>-` crashed the probe process with
ERR_OUT_OF_RANGE from the server callback (transcribed stack). Green —
past-EOF start → 416 `bytes */130682`; `bytes=0-999999999` → 206 clamped
to `0-130681/130682` with Content-Length equal to actual bytes; suffix
`bytes=-500` → the last 500 bytes; bounded range exact. watchstate +
markwatched stay green.

Reopen fix-up 2026-07-05 (reviewer caught a reversed-range miss,
`bytes=50-40` → negative Content-Length + crash path): `start > end` now
also returns 416, matching stream_proxy's tested behavior. Probe:
reversed range → 416 `bytes */130682`; all prior probes unchanged.

## Coder dispute (if any)
None — admitted as filed.

## Known gaps
Multi-range requests (`bytes=a-b,c-d`) are not supported; mpv does not
issue them, and a real server may also choose to ignore them.
