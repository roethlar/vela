# eh-11: Queue scenario races clip A's EOF against the UI window

**Severity**: MEDIUM — a slow Play-next/screenshot path turns the scenario into a flaky false-red
**Status**: Verified
**Branch**: n/a — no-branches adaptation; fix lands as a single commit on `main`
**Commit**: `2eabf26`

## Evidence
`tests/e2e/scenarios/queue.mjs` (pre-fix) — A (a 10s clip) keeps playing
through the context-menu flow and the screenshot; the `beforeB` socket
snapshot is only taken afterwards, and EOF is forced later. If A reaches
natural EOF during that window, either B has already spawned (and lands
inside the snapshot) or the advance fired before B was queued — both make
`waitForNewMpvSocket(beforeB)` time out. Filed by codex in the e2e-5
batch pass.

## Predicted observable failure
`no new mpv IPC socket appeared` on machines/loads where the UI window
exceeds A's remaining runtime — a flaky false-red, not an app regression.

## What
The scenario's only timing budget is the clip length, and the UI steps
spend from the same budget.

## Approach
Pause A over IPC immediately after connecting, run the whole UI window
(queue B, screenshot, snapshot `beforeB`) with playback frozen, then
unpause and seek to 9.5s. EOF becomes impossible before the snapshot by
construction.

## Files changed
- `tests/e2e/scenarios/queue.mjs` — pause/unpause around the UI window

## Guard proof
Deterministic via an injected 11s delay before the `beforeB` snapshot
(simulating a slow UI window): pre-fix the scenario FAILS with
`no new mpv IPC socket appeared`; with the pause fix and the same delay it
PASSes; delay removed, normal green.

Executed 2026-07-05: pre-fix + 11s delay → FAIL (exit 1, socket timeout);
pause fix + same delay → PASS; delay removed → PASS.
